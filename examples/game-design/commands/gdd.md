---
description: Draft or grow a Game Design Document — the core fun first, concrete enough for a builder, ruthless about scope.
---
Write or extend the Game Design Document (`GDD.md`) for the user's game. A GDD is
not a novel — it is a buildable plan. Keep it concrete.

If starting fresh, first pin down (ask the user if unstated): the **core fun** in
one sentence (what the player does moment-to-moment that is enjoyable), the
**goal + obstacle**, and the **smallest playable version**. Do not proceed to
features until these exist.

Then structure `GDD.md` as:

1. **The pitch** — the game in two sentences a stranger understands.
2. **Core loop** — the 10-second cycle the player repeats, step by step.
3. **Mechanics** — one short spec each (link the `/mechanic` outputs).
4. **The smallest playable version** — exactly what the first build contains, and
   just as importantly, **what is cut** from the dream version and why.
5. **Look & feel** — a few words, not a mood board.

Numbers where numbers matter. After drafting, offer to run the read-only
`mechanics-reviewer` — a GDD with no identifiable core fun, or scope a beginner
cannot build, is the most common (and most expensive) mistake.
