# The MDA framework

MDA (Hunicke, LeBlanc, Zubek) is a simple, powerful way to think about how a
game's rules turn into a player's experience. Three layers:

- **Mechanics** — the rules and systems you actually write: the moves, the
  numbers, the win condition. This is what you *build*.
- **Dynamics** — the behaviour that *emerges* when players interact with the
  mechanics: chasing, hoarding, bluffing, racing. You do not write dynamics
  directly; they arise from mechanics.
- **Aesthetics** — the *feelings* the player has: tension, triumph, curiosity,
  fellowship, discovery. This is what the player actually came for.

**The key insight — two directions:**

- **The designer works Mechanics → Dynamics → Aesthetics**: you change a rule,
  which changes how players behave, which changes how they feel.
- **The player experiences Aesthetics → Dynamics → Mechanics**: they feel the
  tension first, and only later (if ever) notice the rule causing it.

So: **decide the aesthetic you want first** ("I want the player to feel clever"),
then find the dynamic that produces it ("outsmarting the enemy's pattern"), then
write the mechanic that creates that dynamic ("enemies telegraph their attack
0.5s early"). And when something feels wrong, debug in the same chain: the
feeling is off → which behaviour is missing → which rule to change.

**Using it in practice:** when a mechanic is not landing, do not just tweak the
number blindly — ask which *feeling* you were after and whether this rule can
ever produce it. Often the fix is a different mechanic entirely, not a bigger
number. MDA keeps you honest that rules are a *means* to a feeling, not the goal.
