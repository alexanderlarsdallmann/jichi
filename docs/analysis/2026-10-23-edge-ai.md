## 1. The answer, up front

1. **Partly.** jichi supports the first of the three layers of edge AI (§2) and has been checked there. It
   has a complete, unexecuted design for the second. It has nothing for the third, and that is by design.
2. **jichi as an agent on an edge device works.** The UNO Q (4 GB, quad Cortex-A53, Debian 13) passed
   jichi's offline gates twice (M282, M455). On 2026-08-04, `doctor --live` found native tool calling, and
   one `--auto --budget-tokens 50k` turn read two files and correctly diagnosed a bug in 9k tokens,
   against a model on another machine [R: `docs/ROADMAP.md` M282]. jichi used about 5 to 16 MB of RAM there
   [R: `docs/LOW_MEMORY.md:186-187`]. Five other boards have been **Driven** with real models over the
   network [R: `docs/PLATFORMS.md`].
3. **The UNO Q is not Driven by the project's own strict rule.** "Driven" means both turns ran through the
   rig, with a recorded agentic phrase. The register reads "Arduino UNO Q | no | offline gates only" [V:
   `docs/PLATFORMS.md:207`]. Its "what ran" text is stale: the M282 turn did run (§6, G7).
4. **A small language model on the device ("small ML") is designed and has never run on any board.**
   - The M278 plan (2026-08-04) puts `llama-server` (llama.cpp) on the UNO Q with a 0.36B to 1B model, and
     climbs three rungs:
     - **A:** the local model as a summarizer and autocompleter;
     - **B:** local first, escalating to a network model;
     - **C:** fully offline.
   - Every jichi feature it needs exists [V/R: §4.2].
   - Nothing has been measured on a board. Every model that a board has used so far ran on the
     workstation or the HRZ gateway.
5. **TinyML on the board's microcontroller (the STM32U585) is outside jichi, by design.** jichi talks to
   language-model endpoints and to devices through tools. Its robotics rule puts the fast loop in firmware,
   below the agent [R: `docs/ROBOTICS.md:10-13`]. A TinyML model fits that architecture as a **device
   tool** whose result jichi reads, and as a **mechanical trigger** for escalation. No such tool, template
   or measurement exists [V: no TinyML term in `src/`].
6. **Three defects would bite the first on-device run** (§6):
   - the 30 s stall default cuts off slow local prefill [V: `include/jc_http.h:46`];
   - routing escalation works only at depth 0 [R];
   - delegates bypass the fallback chain [V: scale analysis §3.1].

   A fourth would be a surprise rather than a defect: jichi's normal prompt is far larger than a small
   model's context. The drive's calls carry about 115,000 tokens [M: scale analysis §4.2], while the plan's
   models have 4,096-token windows. The plan's `toolProfile: core` and `contextLimit: 3500` are the
   answer, and they are unmeasured.
7. **The recommendation** is to run the M278 ladder as written, after three small preparations:
   - a workstation-side capability check of the chosen small models, which needs no board;
   - stall off for measured runs;
   - workers off until delegates use the fallback chain.

   Then add one TinyML demonstrator (an MCU classifier read as a jichi tool) as a separate, measured
   step. Each claim gets the scale analysis's verdicts: *Designed*, *Mechanics-tested*, *Driven*.
8. **E0 ran the same day** (§8a). Qwen3 0.6B and Llama 3.2 1B call tools natively, and SmolLM2 360M only
   as text. None of the three completes jichi's agentic bench: 0 or 1 of 11 tasks, uncapped. So rungs B
   and C are not the honest claim for this size class, and rung A and a larger model remain open. E0 also
   found five new gaps (G10 to G14), among them an output limit jichi derives on its own and a
   server-side tool-call parser that ended 7 of 11 tasks for Llama 3.2 1B.

## 2. Vocabulary: three layers of edge AI

| Layer | What runs where | Typical latency | jichi's place |
|---|---|---|---|
| **1. Agent at the edge** | jichi runs on the device; the model is elsewhere (LAN server or gateway) | seconds per model call | jichi *is* this layer |
| **2. Small model on the device** ("small ML", SLM) | jichi and a language model (0.3B to a few B parameters, quantised) on the same device | tens of seconds to minutes of prefill on a CPU | jichi is the client of a local server |
| **3. TinyML on a microcontroller** | a tiny model (KB to MB) inside firmware, classifying sensor data | milliseconds | jichi reads the result as a tool; it never runs the model |

More terms:

- **Prefill and decode.** Prefill processes the whole prompt before the first token; decode produces the
  tokens one by one. On a CPU, prefill of a few thousand tokens is the expensive half [R: M278 plan].
- **Quantisation.** Storing weights in fewer bits (for example Q4) so that a model fits in memory and runs
  faster, at some cost in quality [GK].
- **Tool-calling forms.** jichi's `doctor --live` classifies a model as `native` (structured tool calls),
  `text` (tool calls written as prose JSON) or `none` [R]. jichi can recover text-form calls when a model
  is configured `toolCalling: "text"` (M949) [V: `include/jc_config.h`, `struct jc_model_cfg`].
- **Deliberative and reflex layers.** jichi is the slow, legible, auditable layer. Reflexes, interlocks and
  the emergency stop belong below it, "in firmware, a microcontroller, or a ROS node" [R: `ROBOTICS.md:10-13`].
- **The kinetic gate.** A tool marked `kinetic: true` (it moves mass or energy) is governed by
  `kineticCommands`: ask by default, unattended actuation refused, every attempt audited [R: `ROBOTICS.md`].

## 4. What jichi has for each layer

### 4.1 Layer 1: the agent at the edge

- **Footprint** [R]:
  - about 1.7 MB peak RSS for the agent loop on a 96 MB machine;
  - 10 to 17 MB for a networked headless turn, mostly TLS;
  - about 5 to 16 MB on the UNO Q.
- **Lite mode** [R: `LOW_MEMORY.md`]: automatic below 1,024 MB of RAM. It turns off snapshots and the repo
  map, and allows one agent at a time with no subagents. The 4 GB UNO Q does not trigger it; a 2 GB variant
  would not either.
- **Boards Driven with real models over the network** [R: `PLATFORMS.md`]: Pi Zero 2 W (512 MB), Pi 400,
  Pi 500+, VisionFive 2, LicheeRV Nano (256 MB, with `stall 0`: 64 s for a text turn and 77 s for a tool
  turn), plus emulated architectures.
- **Thin clients** were the first decision of `scripts/fleet-run.sh` (M459): "a 4 GB device that is also
  hosting a model is measuring the model, not jichi" [R]. Layer 2 sets that rule aside on purpose, to
  measure exactly that.
- **Remote operation** (jichi on the board, the person on a workstation over ssh) "is the normal case",
  and every board row was taken that way [R: M278 plan, use case 9].

### 4.2 Layer 2: a small model on the device

The plan's own words: "Every key below already exists; nothing here needs new code." The features it
rests on:

| Feature | What it does at the edge | Evidence |
|---|---|---|
| OpenAI-compatible provider | talks to `llama-server` on `127.0.0.1` | [V: `struct jc_model_cfg`, `provider`/`api_base`] |
| Per-role models | `summarize` runs compaction locally; `autocomplete` runs ghost text and `fim` locally | [V: `src/chat/jc_compact.c:574`; `src/main.c:10935`, `src/tui/jc_tui.c:3017`] |
| Routing tiers | `routing.fast` local, `routing.strong` network, escalating on stall, error or failed verify | [R: `jc_agent.c:1982-2109`; depth 0 only] |
| Fallback | if the local server is down, the next reachable model serves | [V: `fallback` in `struct jc_model_cfg`] |
| `toolProfile: core` | trims about 16 tools to 7 or 8: prefill seconds, not a nicety | [V: `src/config/jc_config.c:1923-1927`] |
| `toolCalling: "text"` | recovers tool calls a small model writes as prose JSON (M949) | [V: `struct jc_model_cfg`] |
| Prompt caching and prefix stability | the fixed prefix is prefilled once per session; retrieval goes on the user message (M61) | [R: M278 plan] |
| `contextLimit` with self-calibration | jichi's token estimate converges on the server's real count (M77) | [R] |
| Per-model timeouts | a slow local server gets its own stall value | [V: `timeouts` in `struct jc_model_cfg`] |

**What has never happened:** a model running on any board. Every measurement of local inference in the
tree is from the workstation's GPU or the gateway. On the workstation, a cold 16k-token prompt took 32.1 s
to its first byte with a 27B model, and a cached one took 0.4 s [R: `docs/internal/2026-10-15-model-prefill-measurement.md`
§2]. An A53 CPU will be much slower [I]. How much slower is the plan's step 3.

### 4.3 Layer 3: TinyML on the microcontroller

- **In jichi: nothing**, and that is deliberate. jichi links no device library ("shell out, don't vendor",
  M42), and it reaches hardware only through **user-defined tools** (a script speaking JSON) or an **MCP
  server** [R: `ROBOTICS.md:15-20`]. No file in `src/` mentions TinyML, TFLite or Edge Impulse [V].
- **The architecture it fits** [R: `ROBOTICS.md`, kit recommendation]:
  - the microcontroller holds the reflex loop and a heartbeat watchdog;
  - a TinyML classifier is one more thing the firmware computes;
  - the Linux side reads its result over the Bridge or serial, through a device script;
  - jichi calls that script as a read-only tool, and any actuation goes through a kinetic tool.
- **Two uses for a TinyML result:**
  - **As data:** "what did the sensor see?" The tool returns a class label and a confidence.
  - **As a mechanical trigger:** the M278 plan's edge-triage case says that whether something is anomalous
    should be decided by "a mechanical trigger (threshold, regex, exit code)", and that the small language
    model should only *describe* what it found. A TinyML classifier is exactly such a trigger, firmware-fast
    and deterministic given its weights [I].
- **jichi as the developer of a TinyML pipeline:** writing the sketch, building and flashing it through the
  vendor's command-line tools, training on the workstation, reading the serial output. That is an ordinary
  coding task under jichi's fences [I]. It has never been tried.
- **Arduino's App Lab** reportedly ships ready-made AI building blocks for the UNO Q, including Edge Impulse
  models, on the Linux side [GK, unverified against the board]. If so, they are another source of
  classifications for jichi to call as a tool. Whether any of them speaks an OpenAI-compatible API is
  unknown.
- **Limits that matter for a TinyML tool:** a user tool has a 30 s default timeout and a 32 KB output cap
  [R: `USER_TOOLS.md:47, 52-69`]. A classification call fits easily [I].

### 4.4 Other edge modalities

jichi has `transcribe` (speech to text), `audio` (text to speech), `image`, `embed` and `rerank` roles
[V: `include/jc_config.h:100-109`]. On an edge device they would need an OpenAI-compatible local server
for each, for example a speech model served locally [GK]. None has been tried on a board. Memory is the
limit: each server shares the board's few GB with the language model [I].

- **"Keeps working offline" means reduced, not equivalent.** Say which tasks still work, never imply parity
  (use case 4) [R].

## 7. Decisions for the operator

| # | Decision | Recommendation |
|---|---|---|
| D-E1 | Which edge layers jichi claims | Layers 1 and 2 as tested claims; layer 3 as tool integration only |
| D-E2 | The serving stack on the board | `llama-server` first, as the plan says |
| D-E3 | Stall on local routes | Off for measurements; a measured per-model value afterwards |

| D-E6 | A second board for comparison | Optional: one more 4 GB-class board after the UNO Q |

**D-E1. Which edge layers jichi claims.**

- Options:
  - (a) layers 1 and 2 as tested claims, layer 3 as tool integration only;
  - (b) also build TinyML tooling into jichi;
  - (c) layer 1 only.
- Recommendation: **(a)**. (b) breaks "shell out, don't vendor" and the reflex-below-the-agent rule. (c)
  leaves the plan's best cases (compaction offload, degraded mode) untested.
- Rests on: §2, §4.

**D-E2. The serving stack on the board.**

- Options:
  - (a) `llama-server`: OpenAI-compatible, a prefix cache, explicit quantisation, no accelerator dependency;
  - (b) ollama;
  - (c) the vendor's App Lab building blocks.
- Recommendation: **(a) first**, as the plan argues. Record (c) as a second route only if it exposes an
  OpenAI-compatible endpoint, which is unknown [GK].
- Rests on: M278 "Hardware and serving stack".

**D-E3. Stall on local routes.**

- Options:
  - (a) `stall: 0` for every measured run, `deadStream` as the fence, then a measured per-model value;
  - (b) keep the plan's guessed 180 s;
  - (c) keep the 30 s default.
- Recommendation: **(a)**. (b) and (c) are caps that would manufacture an answer on a slow CPU.
- Rests on: G2; this project's "no cap on a measurement" rule.

**D-E4. The TinyML scope.**

- Options:
  - (a) one demonstrator: a classifier in the microcontroller's firmware, read through the Bridge by a
    device script, called by jichi as a read-only tool, measured end to end, with any actuation behind
    the kinetic gate and the reflex watchdog proven first;
  - (b) a general TinyML framework in jichi;
  - (c) none.
- Recommendation: **(a)**. It tests the architecture without adding code to the agent.
- Rests on: §4.3, `ROBOTICS_BRINGLIST.md`.

**D-E5. Privacy routing.**

- Options: (a) a design note now, built when a deployment needs it; (b) build it now; (c) leave the gap
  undocumented.
- Recommendation: **(a)**, per "design now, build when needed" (2026-10-23).
- Rests on: G9.

**D-E6. A second board for comparison.**

- Options: (a) after the UNO Q, run rung A on one other 4 GB-class board already on the bench (a Pi 5 or
  the BPI-F3); (b) the UNO Q only.
- Recommendation: **(a), optional.** A second board separates "this board" from "this class of board". The
  BPI-F3 has no Landlock [R: bench record], which matters only for parallel write workers, and those stay
  off here.
- Rests on: scale analysis §2.3.

## 8. A plan, cheapest evidence first

Each step names its verdict target. Caps stay off for every measurement, and fences stay on.

1. **E0: model capability on the workstation (needs no board).** Serve the plan's two candidates (one ~1B
   instruct model, and SmolLM2 360M as the floor case) with the same quantisation under llama.cpp on the
   workstation. Run `doctor --live` and the agentic bench (`tests/bench`), and measure the real prefix with
   the `core` profile.
   - A model that reports `none` drops to rung A.
   - Output: a capability row per model.
2. **E1: bring the board back.** This is the operator's step:
   - its own solid 5 V supply (M277);
   - a data-carrying cable or Ethernet;
   - the ssh server enabled;
   - a fresh address recorded.

   Then re-run the board rig at current master and drive both turns through it with a model on the LAN.
   Verdict: **Driven** (closes G1 and G7).
3. **E2: the board's own inference baseline.**
   - `llama-server` builds and runs on the board.
   - Measure prefill and decode tokens per second at thermal steady state, the memory of server plus jichi
     plus a turn in flight, and whether a second turn's prefill drops (the prefix cache working).
   - Record the CPU features that decide quantised speed (dotprod, i8mm).
   - Before measuring, stop Docker, or say that it ran.
4. **E3: rung A.** `summarize` and `autocomplete` local, chat on the network. Read one locally made
   compaction summary by hand against a network-made one. Verdict: Driven at T0 for rung A.
5. **E4: rung B, then C.** With workers off (G4) and stall off (G3):
   - local first with escalation, counted from the `route` telemetry;
   - then a bounded, fully offline edit whose verifier passes;
   - a 30-minute soak for thermal decay.
6. **E5: the TinyML demonstrator.**
   - The reflex watchdog first, proven with jichi switched off (`ROBOTICS_BRINGLIST.md` step 4).
   - Then one classifier in firmware, a device script over the Bridge, and a read-only jichi tool.
   - Measure from sensor event to the tool result, and to an escalation that a threshold triggered.
7. **E6: the record.**
   - Machine-stamped rows in `LOW_MEMORY.md`;
   - an `analysis/` write-up (predicted, observed, finding or documentation fix);
   - a committed example configuration that actually ran;
   - a statement of **which rung is the honest claim** for this board.

E0 can start today. E1 waits for the board.

## 8a. E0, measured 2026-10-23: three small models on the workstation

*Added the same day the analysis was written, after the operator's go ("Yes, start E0 on the workstation")
and request ("Also try a ~1B model, like Llama 3.2 1B"). Measured, not inferred. The marks below are [M]
for these runs.*

### 8a.1 Setup

- **jichi** `fc638450` (the hardening drive's `-O2` pin).
- **llama.cpp** `llama-server`, release `b11836` (commit `f5027fb21`). It is the CPU build for x86-64,
  run with `--jinja` (the model's own chat template, which carries tool calls), one slot, 8 threads.
  This is the serving stack D-E2 chose for the board.
- **Models**, all Q4_K_M quantisations from the same quantiser (bartowski on Hugging Face), checksummed:
  - Qwen3 0.6B (484 MB);
  - SmolLM2 360M Instruct (271 MB);
  - Llama 3.2 1B Instruct (808 MB).
- **Instruments:**
  - `doctor --live`, which classifies tool calling as native, text or none;
  - the agentic bench `tests/bench`: 11 tasks, 21 points, the `core` tool profile.
- **Uncapped.** The bench's own runner bounds each task by a token budget, a 10-minute `--deadline` and a
  hard 900 s timeout. A modified copy removed all three, kept `--max-tool-calls` as a fence raised to 1,000,
  set `timeouts.stall` to 0, and passed a minimal environment. **No task reached the fence.**
- **Two passes.** The first pass hit an output limit nobody had set. Without `maxTokens`, jichi asks for
  one fifth of the declared context window (`jc_config_effective_max_tokens`, `src/config/jc_config.c:2371-2392`),
  which is 1,638 tokens at 8,192. Pass 2 set `maxTokens` explicitly (8,192 at a 32k context; 4,096 for
  SmolLM2, whose whole window is 8,192). Pass 1 is kept below only as a capped first pass.
- **Where it ran.** On the workstation, with the hardening drive's CI follower gating at the same time.
  This was a capability measurement; no speed figure here says anything about the board.
- **Evidence** is kept outside the tree, on the workstation (results, configurations, the runner's diff, logs),
  and so are the downloads, for re-use.

### 8a.3 What the failures were

- **Qwen3 0.6B fails on content, not on mechanics.** Its tool calls are native and well formed. In pass 1,
  task 01 read `retries = 7`, wrote `"4"` into the answer file, and then claimed to have written 7. Task 05
  wrote `#pragma once` where the task asked for an `#ifndef` include guard. jichi's own end-of-run report
  said "no verifier armed -- the answer's claim of success was not tested", which is exactly the line that
  matters here.
- **SmolLM2 360M cannot drive tools,** even with jichi's text recovery (M949). It either repeats jichi's
  system prompt back until the output limit, or writes a command as prose (`$ find src -type f …`) that is
  not a recoverable JSON block. This is the "describe instead of invoke" class `doctor --live` warned about.
  With 4,096 output tokens it still hit the limit in 4 of 15 calls: a looping model fills any limit.
- **Llama 3.2 1B was stopped by llama.cpp more than by itself.**
  - In 7 of 11 tasks, six of them on the very first call, `llama-server` reported inside an HTTP 200
    stream: "The model produced output that does not match the expected peg-native format". Its tool-call
    parser rejected the model's output.
  - jichi treated that as a provider error and ended the turn.
  - jichi's text mode cannot route around it, because it still advertises the tools to the server
    (`src/chat/jc_agent.c:2643`), so the server's parser still runs.
  - In two other tasks the model looped on `read_file` errors for a non-existent path: 175 and 194 tool
    calls. jichi warned about the loop but nothing stopped it, below the 1,000-call fence.
- **The real fixed prefix is about 2,300 to 2,560 tokens with the `core` profile.** jichi's own estimate splits it
  into 1,054 tokens of system prompt and 1,122 of tool schemas (Qwen3), before any history. On the board's planned 4,096-token
  window that leaves about 1,500 to 1,800 tokens for history and the answer. G5 is confirmed.

### 8a.4 What E0 decides

- **No model in this range does jichi's agentic tasks.** That holds for 0.36B to 1B parameters, at Q4, on
  the stack the board would use. **Rungs B and C of M278 are not the honest claim for these models.** A
  local-first turn would escalate almost every time, paying the local attempt's wall-clock first (use
  case 3's warning).
- **Rung A is still open**: summarising and autocomplete need no tool calling. Whether these models summarise
  well enough is E3's question, on the board or here, with a summary read by a person.
- **A larger local model is the open question.** One that fits the board's about 2.3 GB of free memory next
  to jichi and the server (for example a 1.5B to 2B model at Q4) is untested. That would be an "E0b" with
  the same instruments.
- **The server is part of the result.** Whether a model's tool calls work depends on the serving stack's
  template and parser version, not only on the model. That is M278's own warning ("`native` on threadwork but
  `none` on the board … the endpoint or template differs"), now observed on one machine.

**Note added 2026-10-23, later the same day: E0 ran off the makers' settings.** The bench used
temperature 0.2 for all three models, with the server's defaults for top-k (40), top-p (0.95) and min-p
(0.05), and Qwen3 in its default thinking mode. Qwen3's card warns against near-greedy decoding and
prescribes temperature 0.6, top-p 0.95 and top-k 20 when thinking. Llama's configuration prescribes 0.6 and
0.9. The bench numbers above are therefore the harness's, not yet the models'. The verdict on rungs B and C
stands; the exact scores are to be re-measured at the makers' settings. Two of the three models were also
never built for this bench: SmolLM2 360M's card gives function calling to the 1.7B, and Llama 3.2 1B's is for
dialogue, retrieval and summarisation. What each model is for, and the procedure that tests it for that, are
in [`2026-10-23-small-models-purpose-and-tests.md`](2026-10-23-small-models-purpose-and-tests.md).

**Note added 2026-10-23, 17:40: rung B measured on the workstation.** The small-model procedure (§8a of
[`2026-10-23-small-models-purpose-and-tests.md`](2026-10-23-small-models-purpose-and-tests.md)) ran local-first
routing with Qwen3 0.6B (non-thinking, at its makers' settings) as the fast tier and the free
`jlu/qwen3.8-27b` as the strong tier, escalating on a failed verify. Result: **10 of 11 tasks (18 of 21 points);
4 passed without leaving the device, 6 escalated and passed**. So rung B is viable **with escalation** on the

## 9. Implications

- **For safety.** A local model changes nothing about actuation:
  - `kineticCommands` is never `allow`;
  - `stop_all` stays allowlisted;
  - "the MCU's watchdog is what actually keeps the hardware safe, independent of which model is talking"
    [R: M278 use case 7].

  A TinyML classifier that triggers escalation is a sensor, not a controller.
- **For privacy.** "Runs locally" is a configuration, not a guarantee. Until G9 is built, a project that
  must not send files off the device needs a local-only configuration, stated as such.
- **For cost and capacity.** Local models cost nothing and use no shared gateway capacity, but each failed
  local attempt costs wall-clock (use case 3). In a classroom, the shared strong model becomes the
  contention point (scale analysis §5.1).
- **For portability.** Nothing here adds code or a dependency to the agent. The local server is a separate
  program, and the TinyML model lives in firmware. jichi stays C89 with libcurl as its only dependency.
- **For learners.** Two machines means two of everything: two configs, two binaries, two `PATH`s. The
  plan's use case 9 names "which host am I on, which binary am I running, which config is in effect" as a
  first-class skill. The curriculum plan (2026-08) proposes a reading chapter on exactly this model-topology
  skill; it is tracked and not built.

## 11. What this analysis did not do, and what to doubt

- **Nothing was run on a board,** and the UNO Q is not connected. Every statement about on-device
  inference speed is a prediction until E2.
- **The prefill figures cited are from the workstation's GPU and the gateway,** not from an A53 CPU. They
  bound nothing for the board, beyond the direction.
- **The UNO Q and App Lab facts marked [GK]** were not checked against the board or its current software.
- **M282's live turn** is known from its roadmap entry and the plan's prerequisites, not re-run. The tree
  does not record which model it used, at 9k tokens.
- **A correction to this analysis's own first draft, given in chat the same day:** it said the UNO Q had
  "never had a live model session". M282 shows one did. The strict Driven register is what says "no".
- **The use-case table follows the M278 plan,** written in 2026-08 before most of jichi's later features.
  Its configuration keys were re-checked against `fc638450`, and its recommendations about routing predate
  the gaps G3 and G4.

## 12. Exercises for a self-learner

1. **Name the layer.** "A keyword spotter on the microcontroller wakes the board." "A 1B model summarises
   the log every hour." "jichi on the board asks a gateway model to fix a bug." Which layer is each? *Check:*
   §2: layer 3, layer 2, layer 1.
2. **Price a prefix.** If the board prefills at P tokens per second and jichi's fixed prefix is F tokens,
   how long is the first call of a session, and the second? *Check:* about F/P seconds for the first. The
   second is far shorter only if the server's prefix cache holds and the prefix is byte-identical.
3. **Find the cap.** In `include/jc_http.h`, find the stall default. Why is it wrong for a local model on a
   CPU, and what bounds a dead stream instead? *Check:* 30 s (line 46); `deadStream`, a fence that fires only
   when nothing arrives (G2).
4. **Draw the two layers.** Sketch the UNO Q with jichi, a local model server, the Bridge and the
   microcontroller. Mark where the emergency stop lives and which arrow carries a TinyML result. *Check:* the
   stop and the watchdog are in the microcontroller. The result travels from firmware over the Bridge to a
   device script, then to a read-only jichi tool.
5. **Spot the false claim.** "Our robot keeps patient data private because it uses a local model." What does
   jichi actually guarantee? *Check:* G9: nothing per file. Only a local-only configuration does, for the
   whole project.
