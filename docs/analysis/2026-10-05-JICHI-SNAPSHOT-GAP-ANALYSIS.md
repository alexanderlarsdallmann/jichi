# jichi snapshots & undo: the one thing it definitely lacks — a green answer from the destroy that actually destroyed what it said it destroyed

> **Date:** 2026-10-05
> **Method:** read-only analysis of the jichi source tree at
> `/home/u/development/journey/jichi` (`u` stands in for the home directory on the machine that did the survey) (HEAD `1b71247d`). No files were
> modified; no restore was run for this analysis. All claims cite a source;
> inferences are flagged.
> **Companions:** the other `JICHI-*-GAP-ANALYSIS.md` files (nine earlier).

## 1. TL;DR

jichi's undo machinery is one of the most honestly-documented features in the
tree: `docs/SNAPSHOTS.md` tells you the net is armed *before* you rely on it
(doctor/checkpoints), that **three of the four disarming situations are
silent**, that **ignored files are outside the net** (`.gitignore`d
`local/config.json`, `.jichi/memory.md`, `.env` — "keep a copy"), that **undo
destroys and there is no redo** (M337b, with `preserveDiscarded` as the
deliberate opt-in backstop that pins the state being discarded to
`refs/jichi/discarded/undo/…` *before* destruction, recoverable via
`jichi recover` into a worktree, never the live tree), that the model is
told when its beliefs go stale (M349, red-first tested in
`undo_note.sh`), that the CLI-undo residual is a registered DEFERRED row
(def-237), and that `--dry-run` previews "everything a reset would revert
and everything a clean would remove" (M337/M537).

But the one sentence in the machinery that does the actual destroying —
`restore_to` at `src/snapshot/jc_snapshot.c:705–716` — has a property that
no document, no test, and no DEFERRED row names:

```c
if (git_run(m, "reset", "--hard", commit, NULL, NULL, NULL) != 0) {
    jc_logf(JC_LOG_WARN, "snapshots: reset failed");
    return JC_ERR_IO;
}
git_run(m, "clean", "-fd", "-q", NULL, NULL, NULL);   /* return value: not read */
return JC_OK;
```

`reset --hard` is checked; **`git clean -fd` is not**. A whole-tree restore
— `/undo`, the CLI `undo`, and the envelope's green-checkpoint rollback
(`jc_agent.c:1033`), which is the one caller that *does* inspect the
return — reports **success even when the destroy half that removes files
the agent created after the checkpoint fails**. And because the dry-run
preview's "Untracked files that would be removed" list is generated by
`git clean -nd` — the *exact same command, no `-f`* — the preview and the
destruction are, by construction, the same universe: a failed `clean -fd`
is not a hypothetical mismatch, it is the preview's own list surviving in
the tree while the tree says it was restored.

So the undo surface *does* have the rare property its docs keep promising —
honest failure reporting. It has it for everything *around* the restore:
the disarming (doctor), the stale-model belief (M349), the preview
(M337/M537), the discard backstop (M337b), the partial restore
(`restore_paths` with `*reverted`/`*failed` out-params). What it does not
have, at the one line where it matters most, is a green answer that means
what it says: **`restore_to` returns `JC_OK` on exactly the paths the
documentation describes as "everything that is not in the target
checkpoint is gone" — including the paths where the going has not, in
fact, happened.**

## 2. What the undo surface *does* have (for precision)

- **A shadow git repo, never the user's `.git`** (`SNAPSHOTS.md:11–21`):
  checkpoint = `git add -A` + `git commit` in `~/.jichi.d/checkpoints/
  <key>/` with the workspace as work-tree; `.git/` excluded; the
  workspace's `.gitignore` respected (which is also the documented
  *limit* — the net's hole, §2's last item).
- **Armed-checks-first**: `jichi doctor` + `jichi checkpoints` "before you
  rely on it"; three of four disarming situations silent — recorded as a
  property, not hidden.
- **The ignored-file limit stated in the doc the user reads**
  (`SNAPSHOTS.md:37–47`): "anything your `.gitignore` excludes is never
  captured, and therefore never restored … Keep a copy."
- **The discard backstop (M337b)**: `preserve_before_destroy` pins the
  about-to-be-destroyed tree to `refs/jichi/discarded/undo/<time>-<n>`
  *before* the reset — unix time in the ref name so a next session cannot
  silently overwrite this one's pin; `jichi attempts` lists them;
  `jichi recover` materialises into a worktree, never the live tree.
- **The model-belt (M349)**: after a file-changing `/undo`, one `[undo]`
  user-role note lands in the conversation (label + reverted files, up to
  8 then a count) and the session is saved immediately so `--continue`
  cannot revive stale beliefs without the correction; tested red-first
  (`undo_note.sh`: "edit, /undo, second turn, clean exit").
- **The preview (M337/M537)**: `--dry-run` prints tracked reverts
  (`git diff --stat` universe) *and* "Untracked files that would be
  removed" — produced by `git clean -nd` (`jc_snapshot.c:1708`), the same
  command the destructive path runs with `-f` added.
- **The partial restore** (`jc_snapshot_restore_paths`, `:727`): per-path
  checkout with `*reverted`/`*failed` out-params — **it reports its
  failures**. This is the code's own precedent for what the whole-tree
  path lacks.
- **`/rewind`** (M34c): files *and* conversation to a user-message
  boundary, same machinery, truncation instead of the `[undo]` note.
- **The teeth**: `teeth_restore.sh` (M770) proves the *test ritual itself*
  restores its own perturbation under SIGPIPE/HUP/TERM/exit — the
  project's own doctrine that a destructive script must leave no
  perturbation behind, applied to its own suite.

The doctrine is consistent everywhere except the one line where the
destruction is declared complete.

## 3. The gap, stated

> **`restore_to` (`src/snapshot/jc_snapshot.c:710–717`) checks `reset
> --hard` and returns `JC_ERR_IO` on its failure, then runs `git clean
> -fd` without reading the result and returns `JC_OK` unconditionally.
> Every whole-tree restore in the tree — the TUI `/undo`, the CLI
> `undo`, and the envelope's green-checkpoint rollback (`jc_agent.c:1033`,
> the one caller that inspects the status) — therefore reports a green,
> complete restore on exactly the failure mode where the untracked files
> the preview listed as "would be removed" are still in the tree: the
> checkpoint has been applied to *tracked* state while the *untracked*
> state from the destroyed session survives, and the user is told
> nothing. No smoke test drives a failing `clean -fd` (`undo_scope.sh`
> asserts the success path; nothing perturbs the clean), and no
> document or DEFERRED row names the unchecked half — while the partial
> restore 20 lines below carries `*failed` out-params for precisely this
> class.**

Two strength levels:

* **(Strong, and code-visible in ten seconds)** The asymmetry inside
  `restore_to` itself: one `git_run` whose return is tested, the next
  whose return is discarded, then `return JC_OK` (`:715`). The function's own
  comment block says "`reset --hard` + `clean -fd` is the destruction"
  (`:708`) — and the destruction is only half-checked. This is not an
  interpretation of intent; it is the shape of the statement.
* **(Weaker, but the durable consequence)** **The green the envelope
  trusts is the unchecked half's green.** The autonomy envelope's
  rollback-to-green-checkpoint (`jc_agent.c:1033`) is the machinery that
  an unattended run falls back on when the verify gate fails; it *does*
  inspect the restore status, which means it is one `!= 0` away from
  catching a failed `reset` — and exactly one missing `!= 0` from
  believing a failed `clean` succeeded. The run that rolled back to
  "green" may be sitting on a tree whose untracked half still holds the
  run's own perturbation: the M770 teeth defect, in the production
  path, with no teeth of its own.

## 4. Why "definitely lacking"

| Candidate | Status |
|---|---|
| Ignored files outside the net | **The doc's own stated limit** (`SNAPSHOTS.md:37–47`): "Keep a copy of anything that matters." A boundary, drawn and repeated. Not a hidden hole. |
| No redo | **M337b, with the deliberate backstop** (`preserveDiscarded` pins before destroy; `jichi recover` materialises out-of-tree). Recorded as a decision, not a missing feature. |
| Silent disarm (3 of 4) | **Recorded in the section titled "Is my net armed?"** with the check commands. The project tells the user to verify *before* relying. Not hidden. |
| Stale model beliefs after `/undo` | **Fixed + red-first tested (M349, `undo_note.sh`)**; the CLI residual is def-237 with its own note about the resume-side mtime-drift coverage (M350). |
| Destroyed state unrecoverable | **The pin exists** (`refs/jichi/discarded/undo/…`, unix-time in the name) and `jichi attempts`/`recover` name it. |
| **`clean -fd` failure reported as a complete restore** | **None of the above.** No test perturbs the clean; no doc sentence names the unchecked half; no DEFERRED row; the function's own comment declares both commands "the destruction" and the code checks one. The partial restore's `*failed` out-param is the tree's own proof the class of failure was known to be reportable. |
| The envelope's rollback trusting the unchecked green | **`jc_agent.c:1033` checks the status — and therefore trusts the `JC_OK` that `restore_to` returns after an unverified clean.** The check is a promise the callee breaks. |

The distinctive form, the eleventh instance: the earlier analyses found
boundaries the record stops at (a crash, a learner, a class, a talk, a
real model, a live gate, a machine, a counterparty) or a line the record
crosses (the daemon bullet). This one finds the **inverse** — a feature
whose *surrounding* documentation is the most failure-honest in the tree
(doctor, armed-checks, stated limits, the teeth doctrine applied to its
own suite), with the single most destructive line in that documentation's
universe returning success for the thing it was asked to report. The
M326b register's founding sentence, applied to the callee: *the check
whose universe had shrunk* — here the universe of "the destruction"
shrank, in the code, to `reset` alone, while the comment and the docs
kept saying `reset + clean`.

## 5. Evidence

### 5.1 The line

`src/snapshot/jc_snapshot.c:705–716` (verbatim):

> ```c
> /* Every whole-tree restore -- undo, rewind, the envelope's rollback -- is
>  * below this line. `reset --hard` + `clean -fd` is the destruction. */
> preserve_before_destroy(m, "undo");
> if (git_run(m, "reset", "--hard", commit, NULL, NULL, NULL) != 0) {
>     jc_logf(JC_LOG_WARN, "snapshots: reset failed");
>     return JC_ERR_IO;
> }
> git_run(m, "clean", "-fd", "-q", NULL, NULL, NULL);
> return JC_OK;
> ```

The comment names the *pair* "the destruction." The code checks the
first, runs the second unread, and answers `JC_OK`. `git_run` is the
same helper as the tested line (its failure mode is a non-zero return —
the first `if` is the tree's own definition of what "failed" means for
this helper).

### 5.2 The preview is the same universe

`jc_snapshot.c:1708–1710` (the `--dry-run` "would be removed" list):

> `git_run(m, "clean", "-nd", NULL, NULL, NULL, &part);`

`-n` is git's dry-run flag: the identical traversal, no deletion. So the
list the user reads before saying yes is the list `clean -fd` would
delete — and the one it *failed* to delete, if it failed. The preview
cannot show a file that `clean -fd` then fails to remove, because it is
generated by the same command: the failure leaves the preview's own
output standing in the tree, under a `JC_OK`.

### 5.3 No test touches the failing clean

`tests/smoke/undo_scope.sh` (M537) drives tracked-revert + untracked-clean
on the **success** path and asserts the counts; `teeth_restore.sh`
perturbs the *test ritual's* own restore, not jichi's; `rewind.sh`,
`undo_note.sh`, `undo_across_branch.sh`, `baseline_checkpoint.sh` all
assert green-path behaviour. `grep -l "clean" tests/smoke/undo*.sh
tests/smoke/rewind.sh tests/smoke/teeth*.sh` finds the word only in
comments and the success assertions. Nothing makes `git clean -fd`
fail (an unwritable work-tree entry, a locked file, a full filesystem —
the fault-injection binary exists for exactly this: `faults.sh` runs
"Requires a FAULT=1 binary", and it does not include a clean failure).
**Flagged inference:** I have not *made* the clean fail; the claim is
that no test path in the tree can make it fail, which is verifiable by
the absence just described.

### 5.4 The tree knows how to report this class

`jc_snapshot_restore_paths` (`:727`), 20 lines below: `int *reverted,
int *failed` out-params, per-path `checkout` with an `existed` check and
a counted `bad`. The partial-restore design (M142's out-of-scope
revert, decision D7) *chose* failure visibility for its class of
destruction. The whole-tree class got the pin, the preview, the
count-after (M537: "undo reports the size of what it destroyed") — and
not the one `!= 0`.

### 5.5 The caller that checks is still blind to the clean

`jc_agent.c:1033`:

> `if (jc_snapshot_restore_commit(app->snapshots, e->green_commit)` —
> the envelope's rollback inspects the status.

Which is exactly why this is a *reporting* gap and not a *consequence*-
free one: the machinery that falls back when an unattended run fails the
verify gate will, on a failed `clean -fd`, log nothing (the warn exists
only for the reset branch), mark the rollback complete, and resume the
run against a tree whose untracked half is the run's own. The check is
there; the callee lies to it on one branch.

### 5.6 The docs' own words frame both halves

`SNAPSHOTS.md:215`: "`/undo` and `jichi undo` are `git reset --hard` +
`git clean -fd` against the shadow repo. **Everything in the tree that is
not in the target checkpoint is gone, including untracked work**." The
sentence the user is told is *the outcome* is only *the attempt* for
half its content.

## 6. Implications

1. **A green `/undo` is not, in one failure mode, an undo.** The tracked
   half is at the checkpoint; the untracked half (files the agent
   created this turn — often the *newest, most interesting* work: a
   scratch script, a generated artifact, a half-finished module) is still
   there; the UI says "reverted to checkpoint N"; the M537 count printed
   the size of what *would have been* destroyed. The user's next edit
   builds on a tree no one named.
2. **The envelope's guarantee is one missing check weaker than it looks.**
   The whole point of rollback-to-green is that an unattended run cannot
   leave the tree perturbed; `teeth_restore.sh`'s doctrine (a
   destructive script must restore its perturbation *however it is
   stopped*) is the project's statement of that guarantee for its own
   suite. The production path that needs the guarantee most has no teeth:
   if `clean -fd` fails, the perturbation stays and the report says
   clean.
3. **The pin mitigates the *data* loss, not the *false green* — and on
   the envelope path it is skipped by design.** `preserve_before_destroy`
   runs *before* the reset, so a failed clean leaves the destroyed state
   recoverable via `jichi recover` (the pin contains the untracked files
   the clean failed to remove). But the envelope caller sets
   `preserve_skip_once = 1` before restoring (`jc_agent.c:1030–1032`:
   "The caller wrote a richer record for this same state already"), so on
   the unattended-run's own rollback the pin inside `restore_to` does not
   even run — the richer record is the envelope's, and it was written
   *before* the run failed, not after the clean half-failed. Nothing
   detects or reports that the live tree no longer matches either record;
   a user who does not check `jichi attempts` has no signal the two
   diverged.
4. **The fix is one line and red-first-testable** — see §7. The absence
   is not a design difficulty; `restore_paths` shows the idiom the code
   already uses for the same class.
5. **Meta, the eleventh, the inverse.** Every other gap in this set is
   the record *stopping at* a boundary or *crossing* one of its own
   lines. This one is the record's most honest surround enclosing a
   single dishonest return: a feature documented as "the net is armed,"
   "ignored files are outside," "undo destroys and there is no redo,"
   with the *destroy* itself answering yes to the no. The register's
   rule that the state described must be the state the tree has is, at
   `:717`, asking a function to describe a success it has not measured.

## 7. Recommendation

1. **Check the clean, say what it did.** In `restore_to`, read
   `git_run`'s return from the `clean -fd` line: on failure,
   `jc_logf(JC_LOG_WARN, "snapshots: clean failed; untracked files from
   the destroyed state may still be present")` and return
   `JC_ERR_IO` (or a dedicated status) so `jc_agent.c:1033`'s existing
   check fires. Keep the pin: it is now the recovery path for exactly
   the half that failed.
2. **Red-first test, FAULT=1 style.** `faults.sh` already runs "Requires
   a FAULT=1 binary"; the same pattern drives a failing `clean` (the
   fault injection in `git_run`'s child, or an unwritable untracked
   entry the mock cannot remove) and asserts: (a) the restore status is
   not `JC_OK`, (b) the warn names the untracked residue, (c) the
   envelope's rollback path reports the incomplete restore rather than
   resuming against the perturbed tree. Before the fix it is red on (a);
   after, green.
3. **One sentence in SNAPSHOTS.md's "Is my net armed?" section**, in the
   page's own voice: the armed check is *three* questions (git present,
   snapshots on, workspace small enough) — and the restore's own report
   is worth trusting because the clean half is checked, not assumed.
4. **File the DEFERRED row for the *pre*-fix state in the register's
   form**, so the history reads: the line existed, was found, was
   checked — the same three-act shape as M349/M537/M770, which is the
   record this feature's docs are full of and this line had skipped.

Rejected, in the register's spirit:

* *Return success anyway and log a debug line* — the log line is the
  warn the reset branch already earns; a debug-level note under a `JC_OK`
  is the M326b shape in miniature (the check passes because the universe
  shrank to "the thing I verified"). The caller at `jc_agent.c:1033`
  exists to be told.
* *Make `preserveDiscarded` the answer* — the pin saves the *data*; the
  gap is the *false green*. A user who did not know to check `jichi
  attempts` has both: the residue in the tree and the report saying
  otherwise.
* *Switch restores to a non-git mechanism* — the shadow-git design is
  the feature (never the user's `.git`, `recover` out-of-tree, the
  pin's reflog). The defect is a missing `!= 0`, not an architecture.

## 8. Limitations and honest counterarguments

1. **A failing `git clean -fd` is rarer than a failing `reset --hard`.**
   `clean`'s failure modes (permission on an untracked entry, a lock, a
   full filesystem) are real but less common than the reset's (a locked
   index, a dirty path git refuses). The gap is a *reporting* gap
   weighted by an *unlikely* event — the honest statement, not a
   dismissal. The teeth doctrine exists because "however it is stopped"
   includes the unlikely stop.
2. **The pin means nothing is lost even in the bad case.**
   `preserve_before_destroy` runs *before* the reset; the discarded
   state — including the untracked files a failed clean leaves — is
   recoverable via `jichi recover`. What is lost is the *report*, and
   the trust the green built. A feature whose worst case is
   "recoverable but unreported success" still has the reporting gap;
   the user who does not check `attempts` does not know to recover.
3. **`-q` hides clean's stderr.** The flag is deliberate (quiet
   success), but it also means a failed clean is silent at the git
   level — the `git_run` helper discards stderr by design
   (`jc_snapshot.c:110`), so the non-zero return is the *only* signal.
   That makes the unchecked return the single point of detection, and
   strengthens rather than weakens §3.
4. **I have not driven a failing clean.** §5.3's claim is an absence
   claim (no test path can make it fail), verified by reading the
   drivers, not by fault injection. The recommendation's red-first test
   is what converts it.
5. **The envelope-rollback consequence is a flagged inference.**
   `jc_agent.c:1033` checks the status (verified); that the *resume*
   then proceeds against the perturbed tree on a clean failure follows
   from the status being `JC_OK` (verified at `:717`) and the rollback
   being the unattended-run's fallback (the envelope docs). I have not
   run a failing-clean unattended drive; the two verified lines plus the
   envelope's stated purpose make the consequence near-certain, and I
   mark it inference where it crosses into the unrun. Note the sharper
   form of this: on the envelope path the in-restore pin is skipped
   (`preserve_skip_once`, `jc_agent.c:1030–1032`), so the *only* record
   of the half-failed state is the warn this analysis recommends adding.
