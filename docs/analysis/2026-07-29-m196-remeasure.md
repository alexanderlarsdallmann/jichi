# M196: the re-measure

*2026-07-29. Two bounded `--auto` drives against the real JLU HRZ model
(`jlu/gemma-4-31b-it`, `contextLength` 32000), `--log-level full`. M192 made these
questions answerable; this answers them, and corrects two standing assumptions.*

## The drives

| | task | tool calls | tokens | outcome |
|---|---|---|---|---|
| **short** | implement 2 stubbed Python functions until tests pass | 7 | 47 k | verified ok, exit 0 |
| **long** | build a pipeline across 5 modules it had to read first | 31 | 504 k | **budget exhausted**, verify red, rolled back to green |

Both bounded (`--budget-tokens`, `--edit-scope`, `--verify`) in throwaway git
workspaces. The long drive hitting its budget and rolling back is M80 working as
designed, and is itself a data point: this model did not finish that task in 31 tool
calls.

## 1. Where the input actually goes

M196 predicted the two-call smoke figure (tool schemas at 77 %) "is not what a long,
history-heavy turn will show". Correct — and the difference is decisive.

| | system | tool schemas | history |
|---|---|---|---|
| short drive (whole) | 6.9 % | **76.6 %** | 16.5 % |
| long drive (whole) | 5.7 % | 36.5 % | **57.9 %** |
| long drive, FINAL call | 4.2 % | 26.7 % | **69.1 %** |

Tool schemas are a **fixed 4 301 tokens per call**; history grew 203 → 11 134. So the
77 % figure was a short-run artifact of dividing a constant by a small total. On a
real drive **history is the dominant term and the only one that grows**.

**Consequence for which lever matters:** trimming the tool set (`--tool-profile
core`) buys a one-off ~27 % on a long turn and less as it lengthens; compaction and
history management govern everything after that. The `toolProfile` lever is for
*small-context* models, not for long runs.

## 2. The byte/4 estimate is not 2× optimistic — it is 1.07× to 1.33×, and drifts

Every `model_call` carries the estimate's parts and the server's real
`prompt_tokens`, so the M77 calibration ratio falls out per call:

| call | est | real | ratio | history share |
|---|---|---|---|---|
| 3 | 5 173 | 5 512 | **1.07** | 4 % |
| 9 | 11 766 | 15 075 | **1.28** | 58 % |
| 21 | 12 953 | 16 945 | **1.31** | 62 % |
| 33 | 16 104 | 21 436 | **1.33** | 69 % |

Two findings:

- **M77's ~2× assumption is wrong for this model.** The real ratio tops out around
  **1.33**, so a `contextLimit` set to half the true window (the standing advice) is
  needlessly conservative here — it throws away roughly a third of the usable
  window. For `jlu/gemma-4-31b-it`, ~0.75 × the real context is the honest setting.
- **The ratio is not a constant, it drifts with content mix.** It rises as history's
  share rises, i.e. the byte/4 heuristic under-counts prose more than it
  under-counts the JSON of tool schemas. M77's per-model single ratio is therefore an
  average over whatever mix the run happened to have — right in kind, but it will
  read low on a schema-heavy short run and high on a history-heavy long one.

## 3. The dedup works

One mid-turn compaction fired on the long drive, and it was a *duplicate* elision,
not an age-based one:

```
compact  phase=midturn  elided=1  dup=1  age=0
```

That is the M76/M-dedup path doing exactly its job: the repeated tool output was
recognised as a duplicate rather than evicted merely for being old.

## 4. The `exit`-field gap was stale logs, not an emission gap

M196 flagged the tool ok-rates as **not judgeable**: only 33 of 1 311
`run_terminal_command` and **0 of 309** `run_tests` events carried `exit`. I
deliberately refused to guess which it was. Now measured:

| tool | calls | ok | carries `exit` |
|---|---|---|---|
| `run_terminal_command` | 19 | 17 | **19/19** |
| `read_file` / `write_file` / `list_files` | 11 | 11 | 0/11 — *correct*, they run no command |
| `run_tests` | 1 | 0 | 0/1 |

So the field is **live and complete** for the tool that runs commands. The old log's
33/1311 predates M168a, which landed the same day. The ok-rates in that log remain
unjudgeable and should not be revisited; these are the numbers to use.

## 5. A real defect the drive exposed: `--verify` was invisible to `run_tests`

The long drive made **19 `run_terminal_command` calls against 1 failed
`run_tests`** — and that one failed with:

> `error: no test command given and none configured (pass 'command', or set testCommand/verify in config)`

…in a run launched with `--verify 'python3 -m unittest discover -s . -q'`.

Cause: `--verify` set `args.verify_cmd`, which reached the **envelope only**, while
`run_tests` resolves `command` → `config.test_command` → `config.verify`
(`jc_tool_test.c`). The two never met. So an armed `--auto` run had a working final
gate while the agent's own test tool insisted none was configured — and the agent
compensated by shelling out.

**This also explains the old log's shape.** A `run_tests` that errors *before*
executing anything leaves `exit_status` at −1, so the field is correctly omitted —
which is exactly `0 of 309`. And 1 311 `run_terminal_command` calls against 309
`run_tests` is the same lopsidedness, one order of magnitude up.

Fixed (M205): a CLI `--verify` now also fills `config.verify` when nothing else
provides one. Gap-fill only — an explicit config `verify`/`testCommand` still wins,
because a project may deliberately hand the agent a narrower test command than the
run's final gate. Verified: the same invocation now returns "all 4 tests passed".

## 6. Memory, re-measured after M197–M202

`turn_end` `rss_kb`: **14 648 KB** (short drive) and **14 768 KB** (long drive, 504 k
tokens, 31 tool calls, 21 k-token final context). Flat. The M180/M181 figures in the
earlier analyses are superseded: retention is gone, the intra-turn peak is bounded,
and listing no longer builds parse trees.

## 7. What did NOT fire

- **M193's `unstring` coercion**: zero `args_repair` events. This model did not
  produce the stringified-nested-JSON shape in 38 tool calls. The fix remains
  unconfirmed against production traffic — it was measured against the *zigodot*
  program's model, and this is a different one. Not evidence the fix is wrong;
  evidence the trigger is model-specific.
- **M195's malformed formatting reply**: no `format_file` calls in either drive
  (Python workspaces, no zls). Still uncaptured.

## Recommendations

1. **Raise `contextLength` for `jlu/gemma-4-31b-it`.** ~0.75 × the real window is
   supported by the measured 1.33 ratio; 32 000 against a 65 536 window is leaving
   about a third unused.
2. **Do not reach for `--tool-profile core` to control long runs.** It caps a
   constant, and history is what grows. It remains the right lever for a genuinely
   small context.
3. **Treat M77's calibration ratio as mix-dependent**, not per-model-constant. A
   ratio learned on a schema-heavy prefix will read low once history dominates.
4. **Re-run this on a Zig workspace** to exercise `format_file` and give M195 a
   second chance at the malformed reply.
