# 里程碑循环（可复用的制品）

```
requirement  ->  design (seam + pure core + thin shell; often a proposal)
             ->  implement in C89
             ->  tests (pure-core unit + e2e/PTY smoke)
             ->  gate: -Werror + ASan/UBSan + valgrind + e2e  --(red)--> implement
             ->  docs + ROADMAP note
             ->  scoped, verdict-gated commit  ->  (next)
```

约 160 个里程碑，每个都是一个小而经过设计的单元。历史读起来像一段叙事，
*正因为*这份纪律——也正是它让 AI 在 378 次提交中保持正确而无回归。

# 交付同一范围的四种方式

针对同一 **M1–M173** 范围的人类工作量（人-月，中值）：

```
AI-assisted (1 dev + AI)  | ~1    <- actual (~5 weeks, 19 active days)
Expert solo               |#################### ~21   (~20-26 months)
Team of ~6                |###################################### ~40  (~5-6 months)
Junior solo               |######################################################## ~60 (~5-6 yrs)
```

- **AI 辅助** = *人类*监督时间（设计 + 评审 + 引导）；不含模型算力。
- **团队**比资深独立花费更多*总*工作量（协调税），但*日历*远少——
  这就是工作量-进度的权衡。
- **初级**带着完成度风险，而不只是慢：若干子系统在没有导师的情况下很难做到
  这种质量。

# 人类的时间去了哪里

```
方向 + 需求（造什么）              ##############  30%
设计评审 + 批准提案                ############    25%
审阅 diff + 运行中引导             ############    25%
决定优先级 / 排序能力带             ######          12%
验证结果 / 阅读 CI                 ####            8%
```

开发者**几乎没写 C**。价值上移到了*栈的上层*：选择下一个能力带、批准一份设计、
抓住一个错误的假设、暂停一次运行。

---

# 为什么卫生反而*更*重要，而非更不重要

那些让**团队**得以规模化的纪律，正是让 **AI 辅助**可信赖的东西：

- **紧凑的里程碑** → 可评审的单元，一段干净的历史。
- **代码之前先有一份设计说明** → 人类先廉价地评审*意图*。
- **纯核心可测试性** → 10,000+ 条离线断言；快速、封闭的 CI。
- **一道硬质量关卡** → 回归被立刻抓住；高提交率是安全的。
- **每个单元一份文档 + 一次提交** → 工作可读且可续接。

> AI 没有取代工程纪律——它**提高了它的回报**。

---

# 诚实的边界

- 三种人类模式的**人-月**数字是估算（±40%），从交付范围自底向上——而非
  实测的运行。
- **AI 辅助**这一数字是唯一被直接测量的（日历 + 活跃天），但只计*人类*时间；
  **模型算力是一项真实成本**，以 token 支付。
- 一份**参考实现**（Continue CLI）在 P0–P4 削减了需求风险；新颖的 P5 能力带
  没有——这也是每个都以一份提案开场的原因。
- 一个项目是一个数据点。可迁移的主张是这套**方法**，而非一个普适的乘数。
