# After M712: the next milestones, designed before they are built

*Plan, 2026-09-23 (M713). It turns the findings of
[`analysis/2026-09-23-what-to-build-next.md`](../analysis/2026-09-23-what-to-build-next.md)
into design decisions and milestones. **As of 2026-09-23 nothing on this page is
built**, except D6 (M715 — §7 says where the build differs from the design) and the
rows marked DONE in §12 — and that sentence carries its date on
purpose, because three plans in this directory still say "not built" about work
that shipped weeks ago (analysis §5.3). Written for a developer who will pick one
item up, and for a self-learner who wants to see what a design decision looks like
before anyone has written the code: a recommendation, the alternatives rejected and
why, the check to write **first**, and what evidence would change the answer.*

---

## 0. How each item is written

Every decision below has the same six parts, in the order the
[`SESSION_RUNBOOK.md`](../SESSION_RUNBOOK.md) works in:

1. **Recommendation** — what to build, in one paragraph.
2. **Why** — the finding it answers, with its number.
3. **Rejected** — the alternatives, and the reason each lost. *If there is no
   rejected alternative, it is not a decision — it is just work* ([DECISIONS.md](../DECISIONS.md)).
4. **Sketch** — files, functions, data. A sketch, not a specification: the milestone
   that builds it owns the details.
5. **The check to write first** — the failing test, and how to prove it red against
   today's tree (runbook steps 2–4). A fix whose check was written afterwards is
   fitted to the fix.
6. **What would change the answer**, and **whose call it is**: *engineering* means
   the next session can simply do it; *operator* means a person must decide first.

Names in this plan that do not exist yet — a stop reason, a journal field — are
**working names**, marked as such. A name written down is a name somebody tries.

## 2. D1 — a no-progress detector for successful repeats

**Recommendation.** A sibling of M432's `jc_toolloop` with the same shape — fixed
size, per turn, heap-free — keyed on **(tool, full arguments, a hash of the
result)**, reset whenever something changes: a successful mutating tool call, or a
shell command that jichi cannot show left the tree unchanged. At a *note* threshold
it appends one sentence to the tool result ("you have made this exact call N times
this turn and received the same result each time; nothing has changed since — use
the result you have, or change the approach"). At a higher *stop* threshold it ends
the turn with a new stop reason (working name: `no_progress`), which M688's single
derivation then renders on all five surfaces.

**Why.** Analysis §3.1: M432 counts failures only; M687 made 200 successful calls
with 0 errors after it had the answer; on this machine's older corpus **20 of 264
turns (7.6 %)** repeat one successful call ≥ 5 times with nothing changed in between
*(corrected at M714: **13 of 264** — the stronger full-tier key; see [`analysis/2026-09-23-the-corpus-pilot.md`](../analysis/2026-09-23-the-corpus-pilot.md) §7)*.

**Rejected.**

- *Lower the default `--max-tool-calls`.* A cap truncates legitimate long turns and
  does not say why; it is a fence against blast radius, not a detector of futility.
- *Count successes in M432 with M432's thresholds.* Successful repeats have a
  thicker legitimate tail — the gap between the raw and the unchanged count
  (72 vs 51 turns at ≥ 3; 52 vs 33 with M714's full-tier key) *is* that tail — so thresholds fitted to failures would
  fire on re-verification.
- *Stop at the first repeat.* Polling a background job and re-running a test after
  an edit both repeat legitimately.
- *A prompt instruction ("do not repeat calls").* Tier-3 guidance: the craft A/B
  (M318) measured that prose of this kind moved nothing a grader could see.

**Sketch.**

- A new pure core beside `src/util/jc_toolloop.c` and `include/jc_toolloop.h`,
  called from the same point in `src/chat/jc_agent.c` where the M105 redo note and
  the M432 note are appended — but on the **success** branch, which today feeds
  neither.
- The result hash is computed there, where the content is still in hand; nothing
  about the content leaves the loop, so the `metrics` tier stays content-free.
- Resets: a successful call to any tool the registry marks mutating; a shell command
  unless M689's attribution shows the tree byte-identical afterwards; a compaction
  pass (the model's view changed, so a re-read is legitimate).
- Exclusions to decide in the milestone, with evidence: background-job output
  polling, `ask_user`, and anything whose result embeds a clock.
- A new `enum jc_run_stop` value in `include/jc_outcome.h` — *add, never renumber*,
  as the header requires. `-Wswitch` then refuses to build until every surface
  handles it, which is M688's whole point.
- **The exit code for that stop is not decided here.** It is the same question as
  `DEFERRED.md` item 7 (capped one-shots), and answering it twice would produce two
  policies.

**Step 0, before any code — the fit.** Run, on the machine that holds the post-M432
corpus:

```sh
# in the jichi checkout, on the other machine -- offline, read-only
python3 tests/measure/success_repeats.py --since 2026-08-14
```

Choose the note threshold where the *unchanged* count first separates from the
legitimate tail, and the stop threshold well beyond it — M432's method (*"fire on
every measured loop while staying clear of the 2x tail"*). If that window prints
`NOT EVIDENCE`, the fit waits for D7's corpus and the milestone ships the note only.

**The check to write first.** A smoke driver on `mockmodel`, whose script replies
with the same successful read-only tool call K times:

1. the note appears at the Nth identical call and **not** at N−1;
2. the turn stops at M with the new stop reason, on stdout, the exit code, the reach
   footer, the `[envelope]` line and `--output json`;
3. the same sequence **with an edit between the identical calls** produces no note
   (the reset);
4. the same sequence with **different** results produces no note (the hash).

Prove each red separately — the per-check perturbation rule — by neutralising the
note, the stop, the reset and the hash in turn, and confirming that each red build
actually succeeded before believing it.

**What would change the answer.** If the post-M432 corpus shows the unchanged count
near zero at ≥ 5, the stop half is unnecessary and the note alone ships — or
nothing does. **Engineering**, once step 0 has run.

## 3. D2 — inferred constraints that explain themselves

**Recommendation.** Keep auto-adopt in `--auto`; change what happens when an
**inferred** constraint refuses something:

1. the refusal the model reads names its provenance and the phrase it was inferred
   from — *"refused by a rule inferred from your request ("…do not compile…"); if
   the task needs this, say so in your answer instead of retrying"* — so the model
   can report the conflict rather than loop;
2. the reach footer and the journal count "refused by an inferred constraint"
   **separately** from fences, so the rate is visible per run and measurable across
   runs;
3. when the verifier is stuck and inferred-constraint refusals occurred in the same
   turn, the stuck-verifier note names them as a probable cause;
4. **before** adding any further phrase guard, measure the scanner's false-positive
   rate offline over the prompts the session store already holds.

**Why.** Analysis §3.2: three misparse classes — M168, M207 and `1d31473d` — each
of which cost a whole `--auto` drive, the third 21 minutes and 2,215,762 tokens of
a rolled-back run, in the mode with no human to read the warning.

**Rejected.**

- *Turn auto-adopt off in `--auto`.* It removes the protection the feature exists
  for (M110): an instruction that scrolled out of an unattended run's context.
- *Keep adding guards per incident.* Three incidents, three guards; each narrows
  the phrasing that fires and none makes the next false positive visible.
- *Ask for confirmation.* `--auto` has nobody to ask.

**Sketch.** The provenance already exists — M169 distinguishes what persists — so
the refusal path in `src/chat/jc_constraint.c` has the origin in hand. The
separate count follows the `tool_refused` pattern the reach footer already uses for
fences. **The offline measurement needs no new tool:** `jichi brief-check` (M433)
already runs the scanner over a brief with no model call and prints each inferred
constraint with the line that produced it — checked on v0.10.0: the zigodot
prompt now infers `none`, and *"Do not compile anything"* infers the build
constraint. Feeding it the prompts the session store holds, and classifying every
hit by hand, gives the false-positive rate the recommendation turns on.

**The check to write first.** Replay `1d31473d`'s own fixture with the guard
neutralised: the refusal text must name the inferred rule and its source phrase,
and the footer must print the separate count. Then restore the guard and assert the
count is 0.

**What would change the answer.** An offline false-positive rate near zero over a
large prompt corpus would argue for items 1–3 only. A high one argues for making
inferred constraints advisory in `--auto` — a bigger change, and a reversal of M110.
**Operator** — it changes what an unattended run refuses.

## 4. D3 — parse embedding vectors without building a tree

**Recommendation.** In `jc_embed_parse` (`src/net/jc_embed.c`), read each
`data[i].embedding` array straight from the response text into the flat `f32`
buffer the index already keeps, with `strtod` over the array span, and fall back to
the existing tree parse for anything the fast path does not recognise. The envelope
fields stay on cJSON.

**Why.** Analysis §3.3: one cJSON node per float, **92 % of peak heap**, a
**170,048 kB** peak for `jichi index` on this repository — above the total RAM of
the two smallest machines that have run the agent loop.

**Rejected.** *Smaller batches* lower the peak and keep the tenfold expansion. *A
streaming parser for every response* is more code and more attack surface for the
one array that matters.

**The check to write first.**

1. A unit test that the fast path and the tree path produce **bit-identical**
   vectors on recorded responses, including exponents, negative zero, integers
   written without a decimal point, and odd whitespace.
2. A fuzz target that feeds malformed arrays to the fast path — the M702 pattern,
   proven against a planted bug before it is trusted.
3. Numbers to beat, from M700's own page: **204 MB** peak heap on its controlled
   200-file corpus under massif, and 170,048 kB maximum resident size for
   `jichi index --reindex` over 3,045 files.

**What would change the answer.** Nothing foreseeable; the risk is parser
equivalence, and check 1 is the answer to it. **Engineering.**

## 5. D4 — no house key, no house dialect (finishing M709)

**Recommendation.**

1. An **unset** provider is refused at the surfaces that need one, exactly as an
   unset model is since M709 — rather than guessed from the model id.
2. A vendor's conventional key variable (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`) is
   read **only when the entry names that vendor's provider**. An unset or
   unrecognised provider reads no implicit key.
3. `doctor` says where a key came from when it came from a convention variable,
   and to which host it will be sent.

**Why.** Analysis §3.4: `src/config/jc_config.c:72-75` and
`src/provider/jc_provider.c:21-27`; and, measured, `doctor` is silent about an
unset provider.

**Rejected.**

- *Keep guessing the dialect from the model id.* A heuristic that chooses a wire
  dialect is a house default under another name.
- *Default an unset provider to the OpenAI-compatible dialect.* M709 rejected
  "default to a free local endpoint" for the reason that applies here too: it is
  still a choice made for the user.

**Open, for the operator.** Whether (2) should also require the endpoint to be that
vendor's own host. It is stricter, and it breaks a common convention — an
OpenAI-compatible gateway reached with `OPENAI_API_KEY` and a custom base URL.

**The check to write first — which is also the reproduction the analysis could not
run.** A smoke driver using `mockmodel`'s own request capture (`--capture DIR`
writes every raw request to `DIR/req.N`): a canary value in `ANTHROPIC_API_KEY`, a
model entry pointing at the mock with no provider and no key setting. Against
today's binary the driver is expected to find the canary in `req.1` — **that is the
red**, and it is the first observation of §3.4's inferred behaviour. After the fix,
the run is refused with the new message and no request is made. A second case keeps
the convention honest: provider `openai`, a canary in `OPENAI_API_KEY`, and the
canary **is** sent.

**Compatibility.** A config that relied on the fallback stops working, as M709's
did: a **MINOR** bump, and a changelog entry that leads with what to do.
**Operator** for the strictness question; engineering otherwise.

## 6. D5 — `config validate` fails what `doctor` fails

**Recommendation.** `config validate` exits non-zero, with `doctor`'s own sentence,
for the **one** condition jichi refuses to run with — an active model that names no
model id — and stays a parse check in every other respect. No posture warnings.

**Why.** Analysis §3.5, measured: `OK … exit 0` against `x no model is configured …
exit 1`, on the same config.

**Rejected.** *A pure parse check* — its `OK` is now a statement about a config the
program will not run. *Surfacing doctor's posture warnings* — two renderers of one
judgement drift apart (the M431 argument the register row already makes).

**The check to write first.** The one-line config from analysis §3.5: `validate`
must exit non-zero and print the doctor sentence. Red on today's binary, by
measurement.

**What would change the answer.** Nothing; the register row said both readings were
defensible only while the config could still run. **Operator** — the row asks for
his call, and this is the recommendation.

## 7. D6 — instruments before corpus

**Recommendation.** Three small recording changes, before anyone gathers the corpus
the four waiting decisions need:

1. The journal's `start` event records whether the run is a **one-shot** — no
   session to resume (working name `one_shot`).
2. The `end` event records whether a **final answer** was produced — a non-empty
   last assistant message (working name `answered`).
3. `read_file`'s argument summary at the `metrics` tier carries **offset and limit**
   beside the path — two numbers, no content — read with `tu_arg_int`'s leniency so
   the summary says what the tool actually executed (*"a preview must read every
   argument exactly as the executor will"*).

Then `capped_oneshot.py` reads the two new fields when present and keeps older
journals in a separate, labelled count, and `reread_ratio.py` gains the telemetry
route.

**Why.** Analysis §4.3: without (1) and (2), twenty capped runs would still not
answer item 7; without (3), ordinary telemetry cannot tell paging from re-reading.

**Rejected.** *Wait for ordinary use* — here it ran on one day in 48. *Record every
path read in the journal* — decided against on purpose, as a different privacy
proposition (the register row says so, and that decision stands).

**The check to write first.** A journal driver asserting both new fields on a capped
`--no-session` run with an empty final answer, and on an uncapped run with a real
one; a telemetry driver asserting that a paged read's summary carries both numbers.
Both red today.

**What would change the answer.** Nothing about the design; the field names are an
interface, so check [`EMBEDDING.md`](../EMBEDDING.md)'s tier for the journal before
naming them. **Engineering.**

**Built (M715), and where the build differs from this design.** The tier was
checked first: journal fields and telemetry are both *Provisional* in
`EMBEDDING.md`, so adding fields needs no version bump. Three things changed on
contact with the code, and each is a `DECISIONS.md` row:

1. **`answered` became `answer_bytes`.** A capped run's last words ("Let me try with
   explicit tabs:") are text without being an answer, so a boolean would have
   recorded a judgement the journal cannot make; the size is a fact, and
   `capped_oneshot.py` prints it in buckets. The working name was also taken:
   `answered` already means, in the same journal, that a human answered the model's
   `ask` (M359).
2. **The range is reported by the tool, not added to the summary.** The summary is
   also what the TUI prints and a screen reader speaks (M571), so it stays the path
   alone; and a parser beside the call would read the raw bytes, while
   `jc_tool_execute` repairs (M148) and unwraps (M172) the arguments before the
   tool sees them. `read_file` puts the range it executed into its result, and the
   `tool_call` event copies two numbers, `offset` and `limit`. This design's own
   rule — "read with `tu_arg_int`'s leniency so the summary says what the tool
   actually executed" — is met by construction rather than by a second reader.
3. **Designing item 2 found a defect this plan did not know about.** To record what
   a turn answered I read how the structured outputs find the answer: the last
   non-empty assistant message in the *whole* history. In a resumed session a
   capped turn that wrote nothing reported the previous turn's answer as its own.
   Fixed in the same milestone (§12), because `answer_bytes` computed the same way
   would have repeated it.

The check-first drivers are `tests/smoke/turn_answer.sh` (10 checks) and
`tests/smoke/read_range.sh` (6), each check shown red by its own perturbation.

## 8. D7 — a corpus on purpose, and archived extracts

**Recommendation.**

1. **A dogfooding block, planned rather than hoped for:** supervised `--auto` runs on
   real repositories — zigodot, `systems_maintainence`, this repository's
   documentation — with free `jlu/*` models, `--output jsonl` captured outside the
   repository, on **both** machines. Size it after a short pilot, from the rate at
   which each waiting condition actually occurs; the floors (20 capped runs, 50
   paths, more than 12 pressed turns) set the target, not the number of runs.
   **Fences on, caps off** — the standing measurement rule.
2. **Archived extracts.** Each `tests/measure/` script gains an export of exactly
   the content-free fields it reads, and an analysis page that rests on an extract
   cites its SHA-256. The extract lives outside the repository.

**Why.** Analysis §4.2 and §4.4: the corpus is not being produced, and what exists
lives on one machine and gets pruned.

**Rejected.** *Commit corpora to the repository* — they are large, they name paths
from other projects, and the snapshot lint is right to keep them out. *Keep relying
on ordinary use* — measured, above.

**Operator** — model time, and where the archive lives.

## 9. D8 — the capability bench, once per release

**Recommendation.** Run `tests/bench/` (11 tasks, 21 points) on `jlu/qwen3-coder-next`
at every tagged version, starting with v0.10.0, and record pass rate, tokens,
wall-clock, tool calls and the build stamp in a dated analysis page beside the
2026-07-27 one. **Never a gate.**

**Why.** Analysis §4.5: nothing has recorded whether the agent got better or worse
at tasks since July.

**Rejected.** *Make it a gate* — a live model, non-deterministic output, gateway
latency. *A frontier model* — the local-and-free rule in `CLAUDE.md`.

**Operator** — model time.

## 10. D9 — one dispatch table for `main()`

**Recommendation.** Replace the chain of `strcmp(args.pos[0], …)` branches with a
table — `{name, handler, needs_config, needs_session, may_fork}` — and **one**
prologue (redaction armed, envelope armed, accessibility set, signals installed)
and **one** epilogue (the M693 free). The M444/M608/M693 class then becomes a
property of the table rather than of 54 branches. Build it in slices, one
subcommand family per milestone.

**Why.** Analysis §3.6: three incidents, one root, each fixed locally.

**Rejected.** *More lints on the chain* — each incident already got one, and the
class persisted. *Split `main.c` into files without changing the shape* — that moves
the chain. (The reading guide defends `main.c`'s size — *"size marks lifecycle, not
importance"* — and this plan agrees; the argument here is the ordering class, not
the line count.)

**The check to write first.** A structural lint that every table entry runs after
the prologue, and `tests/smoke/secret_env_subcommands.sh` extended from its current
subcommands to all of them.

**Engineering**, but it is the largest item on this page; the timing is the
operator's.

## 11. D10 — record the bench's userland

**Recommendation.** Carry the **userland** as an axis on the platform page the way
the libc is carried — GNU, uutils, BusyBox, a BSD's — starting with this bench's row
(Ubuntu 26.04.1, uutils coreutils 0.10.0, with today's green gate), and have
`make info` and every rig's results file print it.

**Why.** Analysis §2: uutils under the whole gate since April, `timeout` included,
recorded nowhere.

**Rejected.** *Pin GNU coreutils on the bench* — it would hide the userland that
Ubuntu 26.04 users actually have.

**Engineering**; a `PLATFORMS.md` row is a verdict, so it goes through that page's
own lints and conventions.
