## Why this

M1038 (batch 13, MO-1) made a **connect failure** walk the active model's
fallback chain and route the turn to a reachable fallback. What it does not
cover is the middle case the proposal's D3 names: the gateway is reachable,
the model accepts the request, and then the stream produces nothing
useful — a 5xx mid-stream, a provider-error, or a silent stream that only
the `deadStream` fence (900 s, def-39's measurement target) eventually
catches. The turn fails after the budget has already committed to it, and
a long drive (this one: 75 runs) sees the failure only at the end.

Park mode is the proposal's answer: when a turn fails in that class, jichi
**parks** — it records the exact state (history, the failing request, the
`fail_class` from M1039's nine-token vocabulary, the elapsed time and
tokens already spent) and, instead of aborting the whole run, yields a
structured "parked" outcome that a supervisor or operator can resume once
the outage class clears. The park is the same shape as the drive's own
"kept work" (`refs/jichi/discarded/...`, `jichi attempts show`) — a named,
inspectable, resumable state — applied to a *turn*, not to a *worker*.

## The shape (proposed)

- **Trigger.** A model call whose `fail_class` is one of the outage
  classes (`provider-error`, `http-status` 5xx, the stall/dead-stream
  aborts) **and** whose retries are exhausted, in a run that has
  `park: true` in its config (the key is open question 3). A connect
  failure is NOT a park: M1038 already routes it to a fallback, and a park
  on top would double-handle the same event. A `dns`/`refused`/`connect`
  class means the gateway itself is down — the run parks the whole run,
  not the turn (open question 4).
- **The park record.** On the session arena, one `jc_park` struct: the
  history pointer (resumed in place), the failing `jc_message`, the
  `fail_class` token, `parked_at` (wall clock), the tokens and cost
  already spent on the turn, and a `resume_hint` — the model and fallback
  chain state at park time, so a resume does not re-route through a still
  down model. Written to the session file (so a kill -9 between park and
  resume loses nothing — the same losslessness bar as the L-27 spool,
  M996).
- **The outcome.** A headless `-p` run that parks exits with a **new exit
  code** (not 1: a 1 is indistinguishable from a real failure to a
  supervisor that counts) — the proposal's D3 suggests 3. The jsonl gets a
  `parked` event (the `done` event is reserved for answers). A TUI run
  parks to a status line and stays interactive (the operator can resume
  with a command — the command's name is open question 2).
- **Resume.** A new `--resume-park` flag (or the TUI command) re-enters
  `jc_agent_run_turn` at the parked history, with the fallback chain
  re-probed first (one `doctor --live`-style probe per chain member,
  connect-only, so a still-down gateway does not burn a park cycle).

## The cost

Small: one struct, one exit code, one jsonl event, one flag. The risk is
the **state shape** — a park record that is not byte-exact resumable is
worse than no park (a half-resumed turn with a duplicated user message).
The red-first teeth would be: park on a 5xx mid-stream (mockmodel), the
parked event + exit 3, resume on a healthy mockmodel producing the same
final answer as an unparked run with the same prompt, and a park record
that survives a kill -9 (the L-27 pattern).

## Open questions for the operator

1. **Which `fail_class` tokens park.** The proposal says "outage"; the
   nine-token vocabulary (M1039) has `provider-error`, `http-status`,
   `timeout-stall`, `timeout-tls`, `timeout-connect`, `connect`, `dns`,
   `refused`, `aborted`. Park on all nine (a park is a park), or only the
   server-side classes (`provider-error`, `http-status`, the stalls),
   leaving `dns`/`refused`/`connect` to M1038's routing and run-level
   retry? (Recommended: server-side only; the network-down classes are
   M1038's and def-39's.)
2. **The resume surface.** A headless `--resume-park` flag, a TUI command,
   both, or a supervisor `jichi control` verb (the control channel already
   has `status`/`abort`/`inject` — a `resume` would ride it, and the drive's
   supervisor could un-park a run without touching the operator)?
3. **The config key.** `park: true` as a top-level key, or under M1006's
   `strictness` umbrella (`strictness.park: "on" | "off" | "headless-only"`)
   so the drive can run it `headless-only` (TUI parks stay interactive and
   untestable in the drive's gates)?
4. **Park the turn or park the run.** A turn-level park (the proposal's D3)
   resumes inside the same run; a run-level park (the drive's own "kept
   work") is what a 75-run drive actually wants on a multi-hour gateway
   outage — the run parks, the supervisor sees exit 3, and the next run
   resumes from the parked session. Is D3's turn-level park the whole
   finding, or is the run-level resume the one the drive needs (open
   question 4 of the proposal, unmeasured)?
